# Maps

The maps the 2.9.2 client can load as native terrain, what each holds, how
the client loads one, and the 2.9.2 map and scenario assets they come from.
To fly around one: [play/map-viewer.md](../play/map-viewer.md). Which have
been seen on screen: [STATUS.md](../STATUS.md#maps).

## Maps

"Loaded" is the native terrain-object count read from a real client's memory
after flight entry (23 Oct, scratch copy of the prepared client; evidence:
[map_viewer_tour_20261023.json](../../evidence/2.9.2/map_viewer_tour_20261023.json)).
Every loaded object had graphics and every list was complete. At that time
nobody had looked at the maps on screen. Since then eight have been seen
(Arena1a, CTF_arena, CTF_arena_b, irrosa01, outerchange, ast_fld_a,
ast_fld_b, JRMAP); the others have not. Which, when and the evidence:
[STATUS.md](../STATUS.md#maps).

Remarks from the viewing tour that the registry's notes leave out:

- CTF_arena: the nearest object is 42 km away.
- CTF_arena_b: the origin is 97 km from anything.
- outerchange: huge (millions of units); the export resolved only 7 nodes.
- ast_fld_a to ast_fld_d: asteroid fields, 15–25 km out.
- irrosa01: a component layout with real content; the export resolved only 2 nodes.
- Hittest is a test layout.
- JRMAP: station segments, docked ships, wall, markers, 5 safe zones.

The native loader expands nested layouts, so outerchange, irrosa01 and
newterrain are much richer in the client than in the OBJ exports. newterrain,
outerchange, irrosa01 and hy_base_test each have an unnamed object at exactly
(0, 0, 0). If a view starts inside something, restart with `--spawn-at`.
Spawns are viewing positions, not original spawn points. Components are
pieces that bigger maps reuse, shown alone.

**JRMAP limits.** The 2.9.2 reader skips the 16 records whose object types
(`ss1`, `ss4`, `ss5`, `Dish`) no longer exist. Turrets, buoys/cubes, warp
gates and flag stations (kinds 1, 3, 7, 8) are behind controller flags in the
2.9.2 creation code and are not expected to appear. Expect walls, the
capital ships and five safe zones (kind 2; before 25 Oct 2026 `install`
left their names empty and the client dropped them, so re-run it).

**Safe zones** (patch level 18 or later): Arena1a, newterrain, outerchange,
irrosa01, hy_base_test, CTF_arena_b and JRMAP have them. They draw as
translucent blue wave cubes; on all but CTF_arena_b and JRMAP you spawn
inside one, so the whole view is tinted blue until you fly out. See
[findings 9.42](../research/findings.md#s9-42) for the list and sizes.

**TestScene** (2.0.0) cannot be loaded this way: the 2.9.2 object database
does not contain it, and its format differs.

## How the client loads a map

- Client: `online-terrain-v3` (`aoa/client/patches/online_terrain.py`) hooks the
  flight-entry handler at `0x4306AF`. The server's four-byte 0x2C body
  selects the map: `AR1A` means Arena1a, kept for v1-prepared clients;
  `MAP` plus an index byte selects any entry of the 20-entry table in the
  cave (`0x58B8C0`; `0x58B8A0` before v3), built from the map registry
  `aoa/maps/registry.py` that the server also reads. Layouts go through the native lookup `0x4CDD30` and
  loader `0x495DF0`. `JRMAP` goes through the native `.TRN` reader
  `ReadInTerrain` (`0x4967E0`). Unknown markers, out-of-range indexes,
  missing world state and an existing terrain list all leave the client
  unchanged. After a load, v3 hands each safe zone to the flight view's
  zone-visual list (`0x43E030`), which `SetupFlightMode` had already
  walked while the map was still empty.
- File map: 2.9.2 reads 540-byte records; the 2.0.0 file has 512-byte
  records. `decode_trn.convert_292` inserts the two gaps that move position,
  scale, kind and the sentinel to their 2.9.2 offsets (see
  [level-data.md](../research/level-data.md) and the `decode_trn.py` notes).
- Server: `--map` accepts every table name; with `--experimental-terrain` it
  sends that map's marker and moves relay spawns to the map's viewing spawn.
- Tests: `test_online_terrain.py` executes the hook in x86 emulation for all
  20 entries and for rejected markers, and checks the v1 → v2 upgrade. The
  native lookup, loader and reader are stubbed in emulation.

## Local maps and scenarios

Inventory of the extracted 2.9.2 bundle, checked 20 October 2026. These are
available assets, not a claim that the replacement server can host their
original game modes. Reproduce with:

```powershell
.venv/Scripts/python.exe -I tools/run.py archive.analysis.arena_inventory work/2.9.2/export work/2.9.2/scenes evidence/2.9.2/arena_inventory.json
```

The scene JSON is produced by `tools/scene2obj.py` (see [asset-formats.md](asset-formats.md)). Its
name-to-object matching is heuristic; unrendered nodes may be markers or
unresolved geometry. All model references that it resolved exist locally.
Hashes and counts are in `evidence/2.9.2/arena_inventory.json`.

Arena1a's count was corrected on 21 October: the old inventory omitted 80
turret records. Its current audit and remaining gameplay blockers are in
[Arena1a recovery](../research/arena1a.md); the older inventory JSON retains the historical
303 count. Nested expansion adds 11 records, including 10 placed meshes.

There are also four asteroid-field layouts (`ast_fld_a` through `ast_fld_d`)
and eight base/component layouts: `CTF_base`, `hu_base_a`, `hu_base_b`,
`hy_base_test`, `hy_winga`, `HyBase2Lay`, `irrosa01`, and `ze_winga`.
These total 17 exported layouts; component layouts need not be standalone maps.

Five backdrops exist: `spacebkgd`, `spacebkgd2`, `spacebkgd3`, `spacebkgd5`,
and `spacebkgd6`. The server-list backdrop must name an existing object:
the original `field40` placeholder caused an intentional client shutdown.

`SCENARIOS.AOA` exports only **Curt3**, a 2,282-byte binary scenario. Tagged
strings include Defense, Offense, Attackers, Defenders, and Air Superiority.
Those are labels inside one file, not five recovered scenarios. Its structure
(teams, groups, ships, orders, waypoints) is now decoded by
`aoa/formats/scenario.py`; trigger and win rules are not in the file. The
loose `JRMAP.TRN` is a further editor-saved map. See [level-data.md](../research/level-data.md).
This inventory does not cover missing server-delivered resources.

The experimental server now creates players and one opt-in passive mission
ship (`--experimental-object`), verified in the real client on 21 Oct.
Movement synchronization still has timing/recovery limits, and the relevant
scoring/team/mission rules are missing. Advertising a terrain name in Station
alone does not provide those. No original multiplayer scenario is yet
verified hostable. See findings 9.11 for the object-spawn evidence.

Static `CTF_arena` continuation (21 October 2026):
`python -I tools/run.py aoa.maps.arena_geometry` checks the existing heuristic export
and writes `work/ctf-arena-validation.json`. It found 37,449 finite vertices,
35,134 triangles with valid indices, 113 exported objects and no degenerate
triangles. All resolved model files exist. Six nodes remain unresolved:
`NavFar2`, `ZAMissile`, `ZAMissile0`, `ZARepair0`, `CTF_base01`, `CTF_base02`.
In particular, the bases are not represented in the checked mesh; treating
this export as complete server collision would omit them. The static check
does not verify node semantics, heuristic matching, original-client loading,
collision or spawn safety. `CTF_arena` remains a validation candidate.
